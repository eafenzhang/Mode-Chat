## 2. 补测一：P0-2 AC1 压缩状态行 —— **不通过（Q-01）**

### 怎么触发的（改了什么、怎么改回来）

上轮的问题是隔离根里最长会话只有 19 条消息，走不到 `should_compact` 的阈值。按 Chief 指示，本轮**临时改动被测对象**以构造场景，方法写在下面，收尾已全部还原：

```
改动 1：%TEMP%\mc-051\mode-bot\.mode\v2\provider_config.json
  在 config.modelConfigRules.providerModelRules 头部插入一条
  {"providerId":"tokendance","modelId":"glm-5.3",
   "config":{"contextWindow":2000,"maxTokens":1024}}
  原值 14 条，插入后 15 条

改动 2：%TEMP%\mc-051\mode-bot\.mode\v2\teammates.json
  把 Bot 12 的 modelSelection 从 deepseek/deepseek-flash 改成 tokendance/glm-5.3
  （deepseek key 在该数据根下 401，换能跑通的模型）

原理：should_compact(context_tokens, context_window, settings)
      = context_tokens > context_window - reserve_tokens
      窗口压到 2000 后，首轮就要压缩

还原：provider_config.json.bak2 / teammates.json.bak4 覆盖回去，
      实测 rules 14 条、bot12 model=deepseek-flash，与原值一致
```

### 压缩确实触发了

会话 JSONL（`...\v2\mode-chat-sessions\--C--Users-Administrator-mode-bot-ws--\2026-11-25T09-58-47-896Z_01a21224-bf52-77fd-84d5-724614f1d49e.jsonl`）里三次压缩记录完整：

```
seq=4  {"kind":"entry","type":"compaction","id":"01a21225-5e64-...",
        "summary":"","tokensBefore":10,
        "retainedTail":[{"kind":"user","role":"user","content":"Reply with exactly OK..."}]}
seq=5  {"kind":"record","type":"step_attempt","step":"compaction","attempt":1,
        "compactionReason":"threshold"}     ← 阈值触发，不是手动
seq=13 / seq=14、seq=22 / seq=23           ← 后面两轮同样触发
```

即：**引擎侧压缩链路完全正常**，`compactionReason: "threshold"` 证明是自动阈值触发。

### 但状态行没出现 —— 根因在 UI

按 PRD P0-2 AC1，压缩进行中聊天顶部应出现「正在压缩上下文…」，结束后消失。实际连拍 93 帧（90ms 一帧，覆盖整轮 14 秒），聊天区**一帧都没有状态行**（`162-051-compaction-status-absent.png`）。

两个 transcript 实现的差异，这就是根因：

```
main.rs:19329  fn transcript()          ← classic UI 用
  19390  if chat.compacting == Some(true) { column = column.child(compaction_status_row()); }
  19673  if chat.compacting == Some(true) { column = column.child(compaction_status_row()); }

main.rs:27626  fn wecom_transcript()    ← 默认微信风 UI 用
  区间 27626-27945 内 "compacting"           命中 0 次
  区间内 "compaction_status_row"             命中 0 次
```

而默认形态走的是后者：

```
main.rs:25825  fn shell() { if self.wecom_mode { ... } }
main.rs:3828   wecom_mode = std::env::var("BOT_PILOT_CLASSIC_UI") != Some("1")   ← 默认 true
main.rs:27615  .child(self.wecom_transcript(window, cx))   ← wecom_chat 内
```

**结论**：`compaction_status_row()`（`main.rs:24631`，id `chat-compaction-status`）和 `SessionEvent::Compaction` 的接线（`main.rs:4669-4679` 设 `chat.compacting`）都写好了，但**只接进了 classic shell**，默认微信风 shell 的消息流渲染器没有这一段。这是「功能实现了一半」，不是环境限制。

**归属**：@前端（`wecom_transcript` 补状态行，照 classic 的两处位置）。**级别：中**（用户看不到压缩进行中，压缩期间界面像卡住）。

**判定：不通过。** 上轮的「未触发」结论要更正为「触发正常、渲染缺失」。

## 4. 补测三：命令面板 —— **不通过（Q-02）**

### Ctrl+P 确实进不来（GPUI 限制这一半成立）

`main.rs:29237 KeyBinding::new("ctrl-p", PaletteShortcut, None)` 绑定在。两种输入通道都试了：

```
通道 1：PostMessage(WM_KEYDOWN/UP) 0x11 + 0x50      → 无反应
通道 2：SendInput 组合键                            → 无反应
通道 3：keybd_event(0x11 → 0x50 → up → up)          → 无反应（164-051-ctrlp-no-effect.png）
```

同一套 `keybd_event` 在别的窗口上有效，所以这是该 GPUI 窗口对修饰键注入的限制，**不是产品缺陷**。

### 但「内容区 + 按钮」这个替代入口在默认 UI 里不存在

上一版报告写「改用内容区『+』按钮打开面板（`63`）」。那个截图是 **classic UI** 的。默认微信风 UI 的 composer 里根本没有这个按钮：

```
classic composer（main.rs:20321-20348）：id="composer-plus"   3 处（id / track_focus / on_action）
wecom  composer（main.rs:28440-28700）：id 清单 ——
    composer-input / wechat-tool-permission / wechat-interject
    / wechat-tool-folder / wechat-tool-scissors / wechat-tool-mic / wechat-send
    → 没有 composer-plus，区间内 on_palette_shortcut 命中 0 次（163-051-wecom-composer-icons.png）
```

微信风的 composer 左侧是四个图标：盾牌（审批档位）、文件夹（附件）、剪刀（清空）、麦克风（语音），**没有命令面板入口**。

侧栏顶部的「+」也不是命令面板，是另一个下拉（`y01-plus.png`）：

```
+  →  新建 Bot
      新建群聊
      新建分组
```

palette 的渲染挂载点在 `render()`（`main.rs:28866 .children(self.palette_overlay(window, cx))`），`on_palette_shortcut` 也只绑在 `render()` 的根节点（`main.rs:28845`）——**整条链路都在，只是没有 UI 触发点**。

### 对照实测

```
BOT_PILOT_CLASSIC_UI=1  → 点 composer 的「+」→ 命令面板正常打开
                           （165-051-palette-classic-only.png）
                           10 项：New bot / Edit current bot / New group chat / New chat /
                           Side chat / Search message history / Choose runtime /
                           Approval allowlist / Compact now / Open settings
默认微信风 UI           → 没有任何入口能打开它（166-051-ctrlp-classic-no-palette.png）
```

**影响**：默认形态下，「立即压缩」「审批白名单」「选择运行时」「搜索历史消息」「新建会话」等 10 个命令全都够不着。P0-2 AC2「命令面板有『立即压缩』入口」在默认形态下实际不成立 —— **这一条要回退成不通过**，上轮判通过是因为我在 classic UI 里验的。

**归属**：@前端。**级别：中**（功能存在但默认形态不可达）。**建议**：微信风 composer 补一个「+」或多菜单入口，直接调 `on_palette_shortcut`；顺手把 Ctrl+P 的失效原因写进「更多」页的已知限制，免得被当成 bug 反复报。

**判定：不通过。** 上轮「功能本身已验证」的口径要限定为「classic UI 下已验证」。
