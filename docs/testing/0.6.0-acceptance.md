# ModeChat v0.6.0 验收流程

> 本文件是 **v0.6.0 的验收方法**，不是某一轮的验收报告。
> 目的：把本轮（v0.6.0 阶段 3）反复踩到的「看起来绿了、实际少验了」写死成可执行动作。
> 基线：`docs/prd-0.6.md` 是本轮需求的唯一口径；本文只定义**怎么验**，不改需求。
>
> 每条规则后面都跟「出处」，都是本轮真实发生过的事件。没有出处的规则会被下一次的人当教条删掉。

## 0. 结论怎么给

只允许两种结论，且必须附证据：

| 结论 | 必须附上 |
|---|---|
| **通过** | 命令 + 完整输出片段 + 文件路径或截图文件名 + 该截图的 8 位短哈希 |
| **不通过** | 缺陷清单：复现步骤 → 期望结果 → 实际结果 → 环境（commit / exe 时间 / 数据根） |

禁止的表述：`应该没问题`、`大致可用`、`看起来正常`、`grep 已通过所以完成`。

**出处**：`f904043` 只补了 id `chat-detail-run` 让 grep 判据通过，但右栏三层嵌套（重复标题 / 死「返回」/ 右缘裁 44px）没人点开看过，直到 `252` 那张截图才照出来。

## 1. 自动化门禁（六道，缺一不可）

在**干净工作区**上跑（`git status --porcelain` 必须为空；有 `M` 时跑的是工作区口径，要在报告里写明）。

```powershell
cargo check --workspace --all-targets --locked                 # 期望 EXIT=0
cargo test --workspace --locked --no-fail-fast                 # 见 §2；两个 flag 都不能省
cargo clippy --all-targets -- -D warnings                      # 期望 EXIT=0，0 warning
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\ui-lint.ps1 -Enforce
                                                               # 期望 total violations: 0 / RESULT: PASS
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-parity-anchors.ps1 -Baseline Head
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-parity-anchors.ps1 -Baseline WorkTree
                                                               # 两个口径都要 RESULT: all anchors resolve
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-arch-anchors.ps1
                                                               # 期望 bad=0
```

**注意 `pwsh` 与 `powershell`**：本机 PATH 里没有 `pwsh`（`cargo` 的 PowerShell 是 5.1）。脚本一律用 `powershell -NoProfile -ExecutionPolicy Bypass -File <script>` 跑。另外脚本名是 `scripts\ui-lint.ps1`，不是 `verify-ui-lint.ps1`。

**出处**：本轮数次因 `pwsh` 不存在、脚本名写错而跑到 `CommandNotFoundException`，输出里没有 `RESULT` 行却容易被当通过。

### 1.1 parity 的校验范围（读判据前必须先读这里）

```
anchor-fingerprint checked: 371   drifted: 0   unlocked: 0   stale-in-lock: 53
bare-line anchors checked: 124    skipped(no file earlier on the line): 38
anchors checked: 247  symbol-checked: 107  skipped-external: 46
matrix rows: 136  actual 88/21/27
```

`drifted=0` 的含义**仅是**「这些锚点全部落地」。不在校验内的：

- `plans/**`、`docs/testing/**` 不做锚点校验（门禁只扫 `docs/parity-matrix.md`、`docs/prd-0.5.md`、`docs/prd-0.6.md` 三份）；
- `prd-0.6.md` 里「第 N 行」「区间 `25799-29000`」这类中文叙述**不校验**，只有能归属到同一行完整文件锚点的裸行号（当前 124 条）才校验；
- `skipped-external` 是设计内的外部引用，不是漏检。

**出处**：架构曾写了个 `reanchor-from-lock.ps1`，把区间和 `/` 多位置写法压成单个 token，`anchors checked` 从 248 掉到 200，`RESULT` 照样绿——**少校验 48 条而看不出来**。他最后没入库。教训：**锚点脚本改完必须比对 `anchors checked` 这个总数，不能只看 `RESULT`。**

### 1.2 三条「读到的和以为读到的不一样」

三条都是本轮真实踩到的，全部属于同一类：**校验手段本身给出的是假绿**。

**① 内容一致 ≠ 位置正确（重复行会让 `drifted=0` 假绿）**

`.github/workflows/release.yml` 里这句出现**三次**：

```
:73  if ($LASTEXITCODE -ne 0) { exit 1 }   ← ui-lint 门禁之后
:79  if ($LASTEXITCODE -ne 0) { exit 1 }   ← parity 门禁之后
:85  if ($LASTEXITCODE -ne 0) { exit 1 }   ← arch  门禁之后（锁里这条原本指这条）
```

`cfd5805` 给 Test 步骤加了 7 行，把 arch 那一步从 `:79` 推到 `:85`。`drifted` 只比对**内容**，`:79` 与锁里那句字面完全一致 → 绿灯。**位置错了，但新位置恰好也是一模一样的一句话。**

这是本轮唯一一类**连 `drifted=0` 都拦不住**的漂移，比 `:121`（内容变了、会红）更危险。规律：**唯一的那条会精确报错，重复的那几条会静默假绿。**

判法：**看那一行的上下文步骤名，不看内容**。核 `.github/workflows/**` 这类重复行的文件时，必须读 `- name:` 那几行。

**② 同一条语句的锚点不能用 `Get-Content` 数组下标定位**

`Get-Content` 返回的是 0-based 数组，`Select-String` 报的是 1-based 行号。我这一轮因此两次读错位置（把 `:54` 读成空行、把 `:85` 读成 `newer_than()`）。**核对行号一律用 `Select-String` 的输出，不要用 `$L[$n-1]` 自己算。**

**③ 校验脚本自己少扫时，`RESULT` 照样绿**

见 §1.1 的 `reanchor-from-lock.ps1`（`anchors checked` 248 → 200）。判法是比对**总数**，不是看结论行。

**④ 读取编码错了，会把正常内容读成异常的**

`Get-Content` 在中文 Windows 上按本地代码页（GBK/936）解码 UTF-8 文件，读出来的中文是乱码：

```powershell
# 错：按 GBK 解 UTF-8
(Get-Content $p -Raw | ConvertFrom-Json).titles        → 鍙戝竷鍓嶈蛋鏌?263

# 对：显式指定 UTF-8
$txt = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
($txt | ConvertFrom-Json).titles                        → 发布前走查-263
```

**它的危害方向和 ② 相反**：② 会让你读到无关代码（以为没漂移），④ 会让你**以为数据坏了**，然后去查一个不存在的 bug。实测时我第一次就把它当成「改名写进去的是乱码」，直到用 UTF-8 重读才发现数据完全正常。

**共同点，也是本文件存在的理由**：这四条都源于**读的方式不对**，未必是**被读的东西坏了**——判据说「都对」而被照的事已经不对（①②③），或者判据说「坏了」而事实是好的（④）。这类问题不能靠再加一条判据解决，只能靠**换一种观察角度**（看上下文 / 换工具 / 比对总数 / 换编码）。

## 2. `cargo test` 的判据

### 2.1 当前实现：没有「跳过」这个状态（架构已改）

`src/computer_tools.rs` 现在**不提供 skip 语义**。抓屏类用例的前置条件不满足时**直接 `panic!` 失败**，不是 `return`：

```
1039  这里**不提供 skip 语义**：libtest 没有 skip 概念，
      「探测不到就 return」在 test result 里会被记成 ok 并计入 passed，
      于是「总数 577 / failed=0 / passed 575」三个口径在一条断言都没跑时全部满足。
1049  fn detail_desktop_unavailable() -> Option<&'static str>
1072  fn require_desktop_capture()  →  不可捕获就 panic!("桌面不可捕获：{reason}…")
1082  #[test] fn capture_screen_encodes_png() { require_desktop_capture(); ... }
1091  #[test] fn windows_and_cursor_are_readable() { require_desktop_capture(); ... }
```

**这是正确形态**：跳过变成失败，`failed=0` 立刻有约束力，`passed` 无法被空用例凑满。

### 2.2 三元组判据（**必须现场跑，不接受引用历史输出**）

**先记一条比任何数字都重要的规则**：`cargo test` 的三元组是**桌面状态的快照，不是代码状态的快照**。

```
14:27  CopyFromScreen = OK    LogonUI = 0  →  575 / 0 / 2 = 577   EXIT=0   （连跑两次一致）
14:38  CopyFromScreen = FAIL  LogonUI = 1  →  573 / 2 / 2 = 577   EXIT=101
14:47  BitBlt = False         LogonUI = 1  →  573 / 2 / 2 = 577   EXIT=101  （架构 独立采样）
14:56  BitBlt = False         LogonUI = 1  →  桌面不可捕获，无法复现 575
15:04  BitBlt = True          LogonUI = 0  →  575 / 0 / 2 = 577   EXIT=0   （同一人，回到 575）
15:18  BitBlt = True          LogonUI = 0  →  575 / 0 / 2 = 577   EXIT=0   （Chief 独立采样）
15:20  BitBlt = True          LogonUI = 0  →  575 / 0 / 2 = 577   EXIT=0   （我，第 3 次回绿）
```

**同一个人、同一台机器、同一份代码、同一条命令，11 分钟内 `575/0` → `573/2` → `575/0`。** 所以：

- **`575 / 0` 不能写进「已实测」并长期引用**。它只对「跑出它的那一分钟 + 那台机器 + 那个桌面状态」成立；
- **发布证据必须现场跑、现场贴当次完整输出 + 采集时刻**，不能引用别人十分钟前的结果；
- **判据不能绑定执行者**：我、产品、Chief 都拿到过 `575/0`，架构拿到过 `573/2`，差别在**采集时刻**不在人。写「某某跑了所以算数」会把验签卡在一个具体的人身上；
- `573 / 2` **也不是永久状态**，它同样只描述桌面锁屏的那一刻。

这条规则决定了阶段验收时哪些证据可以引用、哪些必须重跑。**但判断标准不是「证据种类」，而是「取证手段是否依赖外部状态」**：

| 取证手段 | 依赖外部状态吗 | 能否冻结 |
|---|---|---|
| 屏幕级捕获（`CopyFromScreen` / `BitBlt(GetDC(0))`） | **是**——依赖桌面解锁 | **不能**（锁屏即失败） |
| 窗口级捕获（`PrintWindow(hwnd, hdc, 2)`） | 只依赖窗口存在 | **能**（落盘即证据） |
| `cargo test` 三列数字 | **是**——依赖桌面解锁 | **不能**（必须现场跑） |

> **不要写成「截图属于可冻结证据」**。截图曾经也是不可冻结的（依赖桌面状态），换成窗口级捕获后才变稳定。写成按「种类」分，下一个人会用全屏抓取再卡一次；写成按「手段是否依赖外部状态」分，才能自己判断新手段属于哪一类。
>
> 同理，「`cargo test` 不能冻结」也不是因为它是测试，是因为**它依赖桌面这个我们控制不了的状态**。如果将来这两条用例改成不依赖桌面（比如用离屏渲染验证），它就可以冻结了。

**命令与判据**：

```
$ cargo test --workspace --locked --no-fail-fast
最终二进制：bot-gpui-pilot  195 passed; 2 failed; 2 ignored     ← 锁屏时
全 37 个 binary 求和：passed=573  failed=2  ignored=2  total=577   exit=101
```

**要求（与 `docs/prd-0.6.md` §3.3/§3.7 现行口径一致）**：

| 数 | 作用 |
|---|---|
| **`failed = 0`** | **唯一主判据** |
| **`total = 577`** | 完整性检查——≠577 说明**命令漏了参数**（漏 `--workspace` 或漏 `--no-fail-fast`），不是测试丢了 |
| `passed` | **不作判据**，只记录实测值 + 采集时刻（锁屏 573 / 可用 575） |

> **`passed ≥575` 是已废弃的错误口径**，本文件早期版本也用过。原因：锁屏时它必然掉到 573，把它当判据会让验签卡在「桌面是否锁屏」这件我们控制不了的事上；而它又拦不住 skip 方案下的一条空跑。保留这句是为了让后来的人知道为什么改，否则下一轮又会有人提出来。

四种状态对照：

| 桌面状态 | passed | failed | ignored | total | 含义 |
|---|---|---|---|---|---|
| 可捕获 | 575 | 0 | 2 | 577 | 全绿，**唯一可签「通过」的状态**（必须现场跑出） |
| 锁屏 / 无交互桌面 | 573 | **2** | 2 | 577 | 2 条抓屏用例红，**不可签通过** |
| 中间态（桌面正在恢复） | 574 | **1** | 2 | 577 | 一条先恢复、一条还没恢复；**同样不可签通过** |
| 有人把跳过改回 `return` | 575 | 0 | 2 | 577 | 数字与第一行完全相同，但 2 条一条断言都没跑 |

**第四行是这条规则存在的全部理由**：`total`、`failed`、`passed` 三个数字**都分辨不出**「真跑」和「一条都没跑」。只有 §2.1 的实现形态能分辨——所以**改代码改成 skip 就是往回退**，任何 PR 里出现 `if !xxx_available() { return; }` 都应当被拒。

**第三行的「中间态」是实测到的，不是假想**：桌面恢复过程中出现过 `574 / 1` 一次，随后两次都是 `575 / 0`。这种不稳定**恰好证明了 `require_desktop_capture()` 的价值**——它把「桌面正在恢复」如实红出来，而 skip 方案会把它记成绿的。

### 2.3 命令必须带 `--workspace` 和 `--no-fail-fast`（**串联关系，不是二选一**）

```powershell
cargo test --workspace --locked --no-fail-fast      # 唯一正确的写法
```

两个参数各自管一件事，**缺任一个 `total=577` 都不成立**。三档实测（架构跑的，我在 CI 命令里核对过 `release.yml:61` 已同）：

```
cargo test --locked                             binary=1   passed=193  failed=2
cargo test --workspace --locked                 binary=13  passed=225  failed=2
cargo test --workspace --locked --no-fail-fast  binary=37  passed=573  failed=2
```

**漏 `--no-fail-fast`**：第一个失败的 target 就中止，实测跑到的 test binary 从 **37 个掉到 13 个**、`total` 从 577 掉到 **229**。看起来像「测试少了 348 条」，其实是没跑完。

**漏 `--workspace`**：只跑默认成员。实测 `cargo test --locked --no-fail-fast` 只跑 **1 个 binary、193 passed**，**12 个 crate 一个都没测**：

```
[workspace] members =
  crates/atomic-file / automation-repo / automation-service / automation-runtime /
  automation-schedule / bot-team / bots-service / connectors-service /
  credential-store / model-selection / tasks-db / workspace-identity        ← 12 个
```

**CI 已修（`cfd5805`，`release.yml:61`）**：改前是

```yaml
run: cargo test --locked            # 漏 --workspace 也漏 --no-fail-fast
```

后果：CI 上实际只测了 `bot-gpui-pilot` 一个 binary 的 193 条，**PRD 写的 `total=577` 在 CI 日志里永远对不上**（不是 577 也不是 229，是 193 + 1 个 binary）。现在已是：

```yaml
run: cargo test --workspace --locked --no-fail-fast
```

> **出处**：Chief 实测不带 `--no-fail-fast` 时 `binary 数 = 13/37`、`passed = 225`；我实测漏 `--workspace` 时 `binary = 1`、`passed = 193`。两个 flag 各补一个维度，缺任一个，`total=577` 这条判据都不成立。
>
> **这条比锁屏那两条严重得多**：锁屏至少会红，漏跑是**真绿**。v0.5.1 那次 CI 全绿，但从没验证过 workspace 里另外那批用例。它和「`reanchor-from-lock.ps1` 少扫 48 条」、「skip 伪装成 passed」是同一类问题——本轮抓了三次同构形态。

### 2.3.1 固定动作：先核对 CI 命令，再拿 CI 日志核 `total`

```powershell
Select-String -Path .github\workflows\release.yml -Pattern 'cargo test'
# 必须看到：run: cargo test --workspace --locked --no-fail-fast
```

**顺序不能颠倒**。如果命令里少了任一个 flag，CI 日志的 `total` 会变成 193（漏 `--workspace`）或 229（漏 `--no-fail-fast`），而**原因不在代码、在命令**。拿这种日志去核 `total=577` 会得出「测试丢了 300 多条」的错误结论，然后去查一个不存在的回归。

**首次全量跑可能出现新的红**：CI 从「只跑 1 个 binary」改成「跑 37 个」之后，第一次真正执行那 12 个 crate 的用例。**如果那时有更多红，很可能是早就存在、只是从没被执行过的失败，不是当轮引入的**。判断方法：在该 crate 的代码没有改动的提交上跑一次，红即与当轮无关。

### 2.4 不要加 `--skip`、不要用 `#[ignore]`

禁止在门禁命令里固化 `--skip computer_tools::tests::*`，也禁止给这两条加 `#[ignore]`。两者都是**无条件豁免**：在真有桌面的机器上也不再验证任何东西。

**出处**：桌面不可捕获是**环境**状态（我直测 `BitBlt` 返回 `False`、`GetLastWin32Error=203`；同一台机 11:33 桌面未锁时是 `195 passed / 0 failed`，12:57 锁屏后变红）。同一条命令在不同时刻结果不同，说明它在测环境——**这种情况要修的是判据形状（让环境状态显式可见），不是加豁免。**

**出处**：本轮一度有 2 条失败是因为我 12:12:32 之后桌面锁屏（我直测 `BitBlt` 返回 `False`、`GetLastWin32Error=203`；同一台机 11:33 跑的是 `195 passed / 0 failed`）。**同一个命令在不同时刻结果不同，说明它在测环境，不是测代码**——这种情况要修的是判据形状，不是加豁免。

## 3. 截图证据（三条硬要求，缺一不可）

只满足部分要求的图，一律不能作为通关证据。**每条都要贴进 PRD 的截图映射表。**

### 3.0 截图走窗口级 `PrintWindow`，不依赖桌面解锁

**屏幕级捕获和窗口级捕获是两条不同的路**，锁屏只影响前者：

```
屏幕级  Graphics.CopyFromScreen / BitBlt(GetDC(0))        锁屏 → The handle is invalid / 返回 0
窗口级  PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=2)    锁屏 → 仍然成功，抓到完整窗口内容
```

第三个实参必须是 **`2`（`PW_RENDERFULLCONTENT`）**；传 `0` 时 GPU 合成的界面会拍成黑框。

```powershell
Add-Type -AssemblyName System.Drawing
Add-Type -TypeDefinition @'
using System;using System.Runtime.InteropServices;
public class Cap {
  [DllImport("user32.dll")] public static extern bool PrintWindow(IntPtr hwnd, IntPtr hdc, uint flags);
  [DllImport("user32.dll")] public static extern bool GetWindowRect(IntPtr hwnd, out RECT r);
  public struct RECT { public int Left, Top, Right, Bottom; }
}
'@
$p = Get-Process bot-gpui-pilot | Where-Object { $_.Path -like '*target-060*' }
$r = New-Object Cap+RECT
[Cap]::GetWindowRect($p.MainWindowHandle, [ref]$r) | Out-Null
$bmp = New-Object System.Drawing.Bitmap ($r.Right-$r.Left), ($r.Bottom-$r.Top)
$g = [System.Drawing.Graphics]::FromImage($bmp); $hdc = $g.GetHdc()
[Cap]::PrintWindow($p.MainWindowHandle, $hdc, 2)      # ← 必须是 2
$g.ReleaseHdc($hdc)
$bmp.Save("docs\testing\shots\<name>.png", [System.Drawing.Imaging.ImageFormat]::Png)
$g.Dispose(); $bmp.Dispose()
```

**我独立验证过**（不只采纳别人的结论）：`PrintWindow` 返回 `True`，抓出的 1294×847 图里左栏选中态、右栏全部行、底部输入框都清晰可读，不是黑框也不是缩略图。

**两种尺寸都要记，别当异常**：

```
屏幕级捕获（旧的 250–262）   ~1920×1080
窗口级捕获（PrintWindow）    1294×847（窗口矩形，随窗口大小变）
```

映射表里要记录**每张图的尺寸**，否则验收时看到两批尺寸不同，会误以为换了实例或换了机器。

> **出处**：桌面反复锁屏导致 `263-2`/`263-3`、4b/4c 三连拍停了近两小时。换到窗口级捕获后，锁屏与否不再影响截图这条路径，只剩 `cargo test` 那类依赖桌面的证据仍要求现场跑。**这条把「等桌面」从截图路径上彻底移除了。**
>
> **但不要把结论说成「截图是可冻结证据」**——见 §2.2 末尾那张表：可冻结与否取决于**手段是否依赖外部状态**，不取决于证据种类。哪天有人用回全屏抓取，截图就又变回不可冻结。

### 3.1 批次内 SHA256 互不相同

```powershell
$batch = Get-ChildItem docs\testing\shots\*.png | Where-Object { $_.Name -like '26*' }
$batch | ForEach-Object { "$($_.Name) $((Get-FileHash $_.FullName -Algorithm SHA256).Hash.Substring(0,8))" }
$batch | Group-Object { (Get-FileHash $_.FullName -Algorithm SHA256).Hash } |
    Where-Object { $_.Count -gt 1 } | ForEach-Object { "DUP: " + ($_.Group.Name -join ' == ') }
```

**只比「本批」，不对 `docs/testing/shots/` 全目录跑**。全目录当前有 3 组合法重复，会误报：

```
01-startup.png   == 18-chat-bot12.png            （11-25 11:19 与 11:26，同画面不同用途）
101-p01-ac5-...  == 160-051-p01-ac5-...          （v0.5.1 期同图换号）
102-p01-ac5-...  == 161-051-p01-ac5-...          （同上）
```

**出处**：`259-o2-4c-switched-back.png` 与 `257-o2-4b-after-collapse-reopen.png` **字节级完全相同**（`DF68AE34…`，247985 字节，均为 10:28:31），还比「切走」那张 `258`（10:31:48）早 3 分钟；`263-d3-before-click.png` 是第三次同类（同样 `DF68AE34…` / 247985 / 10:28:31），它在**入库前**被拦下（`git status` 一直是 `??` 未跟踪），随后删除。两者现均不在仓库内。

> **文件名齐是最容易伪造的证据形态**，肉眼也看不出两张图字节相同。必须跑哈希。

### 3.2 文件时间 > 该图所验代码进入 exe 的时间

比的是 **exe 编译时间**，不是 `git log` 的提交时间。

```powershell
$exe = (Get-Item target-060\release\bot-gpui-pilot.exe).LastWriteTime
"exe = $($exe.ToString('MM-dd HH:mm:ss'))"
Get-ChildItem docs\testing\shots\26*.png |
    ForEach-Object { "{0,-42} {1}  {2}" -f $_.Name, $_.LastWriteTime.ToString('MM-dd HH:mm:ss'),
        $(if ($_.LastWriteTime -gt $exe) { 'OK' } else { 'STALE 早于 exe' }) }
```

**为什么不能用提交时间**：本轮实测 `257` 摄于 `10:28:31`，而清空逻辑直到 `e659eb7`（`11:03:29`）才提交——但那张图拍的是 `10:24:26` 编译的 exe，代码当时已在工作区并编进去了（我在 `10:18:11` 读到工作区 `11252` 行已有 `self.chat_detail = None`）。**按提交时间判会误杀它。**

**执行要求**：exe 的 mtime 必须与该批截图一起写进映射表，否则下一个验收的人无法复核。

**exe 早于某个 `src/` 提交时，先看那个提交改了什么**：

只改 `#[cfg(test)]` 模块内的代码，`cargo build --release` 根本不编译它，**exe 仍然有效，图不用重拍**；改到非 test 代码则必须重编。

核法：

```powershell
git show <commit> -- src/<file> | Select-String -Pattern '^@@'
Select-String -Path src\computer_tools.rs -Pattern 'cfg\(test\)|^mod tests'
```

实测例子：`263-d3-1-before-click.png`（13:38:36）拍的 exe 是 13:20:57 编译的，而 `5d71ad0`（13:32:30）改过 `src/computer_tools.rs`——只看时间戳会判它过期。但 `git show` 显示两个 hunk 都落在 `mod tests {`（`:1034` 起，`#[cfg(test)]` 在 `:1033`）之内，**release 二进制零影响**，所以那张图有效。

> **只看时间戳会两头出错**：要么误杀（像这次），要么放行一个真过期的 exe。判据是「这段代码进不进 release 二进制」，不是「提交早于还是晚于 exe」。

### 3.3 配对帧必须同一 exe + 时间相邻

因果型判据（「亮 → 操作 → 不亮」）的每一帧必须来自**同一次启动、同一个 exe**，且时间相邻（分钟级）。

| 判据 | 需要几帧 | 为什么 |
|---|---|---|
| 4a | 1（亮） | 单帧即可 |
| **4b** | 3（亮 / 折叠 / 展开不亮） | 只有「展开后不亮」证明不了折叠前亮过——**没点过运行状态时展开也不亮**，两种状态长得一样 |
| **4c** | 3（亮 / 切走 / 切回不亮） | 同上；只有「切回不亮」无法排除「本来就没亮过」 |

**出处**：产品最初提「`261` + `257` 配对看 4b」，但 `261` 是 `12:16:32` 的 exe、`257` 是 `10:24:26` 的 exe，中间隔 2 小时且跨过一次重启。**两帧拼不出一个因果**，只能说明「两个时刻各是多少」。`4c` 同样：`258`（10:24 的 exe）与 `262`（12:16 的 exe）之间没有任何一帧证明「切走之前亮着」。

> **三条规则各自拦一种伪造**：哈希防「同图改名」，exe 时间防「旧图充数」，配对帧防「拿不相干的时刻拼成因果」。**前两条都过不了的图，第三条一定能拦住。**

## 4. 判据要能被证伪

每条视觉判据必须能回答：「如果功能坏了，这张图/这条命令会变成什么样？」

反例（本轮修掉的两条）：

- ❌ 「右栏只有一处『运行状态』」——实际是 **0 处**（删第二张卡时把外层 `ui::section` 一起删了），用户点完只看到一圈绿边、读不出在看什么。**「点了有反应」要成立，反应还得能读出来。**
- ❌ 「`chat_detail_panel` 零命中」——注释里写了「`chat_detail_panel` 已删除」，命中 1 次。判据应写 `fn chat_detail_panel`，**排除「解释自己已删除」的注释**。

正例写法：

```
3a  左栏选中「前端走查群」+ 右栏同时打开 → 右栏标题完整显示「前端走查群」，badge 显示「就绪」
    （只有右栏、看不到左栏选中项时，无法证明标题显示的是哪一个会话）
3b  「会话 ID」行末尾是省略号、右缘没有整块被裁 → 若整块缺失即失败
```

### 7.1 发版时 `cargo test` 复跑变红，先查桌面，不要查代码

同一台机器、同一条命令、**代码一行没改**，实测在 11 分钟内 `575/0` → `573/2` → `575/0`。所以：

- 发版那次跑出 `failed=2`，**第一反应是看 `LogonUI` 进程数和 `BitBlt` 返回值，不是 `git log`**；
- 判据绑定的是「时刻 + commit + exe + 三列数字」这四样，**不是「某一次跑绿」**。绑定的目的是让证据可定位，不是让绿灯可持续——它本来就不可持续；
- 反过来也成立：**别人十分钟前的 `575/0` 不能拿来当本次发布证据**，哪怕那是同一份代码、同一台机器。

> **出处**：产品 14:27 拿到 `575/0`，14:38 就变成 `573/2`；我在 15:04、15:20 又拿到 `575/0`。发起版签字那一步必须现跑。
