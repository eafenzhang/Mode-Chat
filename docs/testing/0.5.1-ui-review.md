## 2. 间距：规范要求 vs 实际落地

规范 `docs/ui-design-spec.md` §2 定义六档：`S1=4 / S2=8 / S3=12 / S4=16 / S5=24 / S6=32`，并明确「废弃 6 / 10 / 14 / 18 等非 4 倍数」。`ui-lint.ps1` **没有**间距规则（四条规则只查 cursor_pointer、rounded、text_size、rgb），所以这一项从来没有被脚本守住。

实测（`src/main.rs` + `ui_kit.rs` + `composer_input.rs` + `simple_input.rs`，只统计 `.px/.py/.pt/.pb/.pl/.pr/.gap/.mx/.my/.mt/.mb/.ml/.mr` 的字面量）：

```
间距调用（px/py/gap/m*）总量: 542   非4px档: 272 (50.2%)

最常见的非档位：
  .gap(px(6.0))   x65
  .px(px(10.0))   x42
  .gap(px(2.0))   x36
  .gap(px(10.0))  x15
  .px(px(14.0))   x15
  .px(px(6.0))    x12
  .gap(px(5.0))   x9
  .py(px(6.0))    x8
```

判定：**间距规范没有真正落地**。`S1..S6` 令牌在 `ui_kit.rs` 里定义齐全、也有大量调用点，但页面里同时混着 6/10/14/5/2 这类手写值——这正是规范 §10 里点名要清的那类。字号和圆角清了，间距没清，`ui-lint` 也没管这一项。

**这一轮不修**，理由：272 处是机械替换但会改视觉，属于「需要逐页截图比对」的批量改造，一轮改 272 处无法保证不引入新的排版回归；而且这不是 bug，是规范符合度。建议单独立项（v0.6 或 v0.5.2），做法是先给 `ui-lint.ps1` 加第 5 条规则（间距值必须 ∈ {0,4,8,12,16,24,32} 或 `ui_kit::S*`），再按页清零，每页截图对比。

**例外说明**：尺寸类属性（`.h(px(20.))` / `.w(px(340.))` / `.size(px(26.))`）不计入——规范约束的是「间距」，组件高度/宽度是另一回事。上面统计已排除 `w/h/size`。

## 4. 交互反馈

| 状态 | 覆盖 | 证据 |
| --- | --- | --- |
| hover | 147/149 处 `pointer()` 调用带 `.hover()` | 两个例外：`main.rs:119` 是 `use` 行注释；`main.rs:14569` 是 v0.6 灰卡（`.opacity(0.55)` 已表达不可用，点只弹 toast） |
| focus | **仅 13 处 `track_focus`** | 全仓 `on_click` 296 处，键盘可达性只覆盖部分入口（Tab 焦点链 + 设置导航 + 侧栏行） |
| disabled | 17 处显式禁用逻辑 | 发送按钮走 `send_enabled` 计算；开关类走 `when(on, …)` |
| loading | 98 处（spinner / 「…」/「正在…」） | 压缩状态行 `chat-compaction-status`、`compacting`、流式气泡骨架 |

**发现（中）：`track_focus` 覆盖不足**。全仓 296 个 `on_click` 只有 13 处 `track_focus`。键盘用户能 Tab 到的只有：设置导航（`settings-nav-{index}`）、侧栏行（`sidebar_row_focus_key`）、面板内少数入口。消息气泡上的动作、审批卡选项、工具卡按钮、右栏各行都不可 Tab 达——虽然有 `alt-↑/↓/alt-a/alt-d` 等全局快捷键兜底，但那不覆盖全部入口。

**这一轮不修**：焦点链是交互架构，不是样式。按 Chief 的底线「需要改交互架构的记 v0.6」，记入 §9。

**发现（低）：`ui_kit::button()` / `button_ghost()` 没有 disabled 形态**。两者都是「永远可点」的 `Stateful<Div>`，没有 `.disabled()` 参数，也没有视觉置灰。当前靠调用方自己判断是否渲染本次按钮，或走 `when(enabled, …)`。风险是新增按钮容易忘记判断、出现「看起来能点但点了没反应」。建议给 `ui_kit` 加一个 `button_with(id, text, enabled)` 形态；属于组件 API 扩展，不是本轮缺陷，记 §9。

按设置页切块统计（`settings_empty` / `ui::empty` / `empty_state` / `settings_note` / `ui::note` / `hint_row` / `settings_error` / `ui::error`）。只统计**真正被路由到**的页；`settings_page_bots` / `settings_page_channels` 是 Bot团队页内横向 tab 的子页（`main.rs:13893-13894`），另列：

settings_page_capabilities empty=Y note=- err=-

settings_page_about        empty=- note=Y err=-
settings_page_feedback     empty=- note=- err=-   （纯表单页，无列表无 IO）
settings_page_browser      empty=- note=Y err=-
settings_page_computer     empty=- note=Y err=-
settings_page_more         empty=- note=Y err=-
```

逐条判定（不把「没有可失败的数据源」当缺陷）：

- **无空态但合理（7 页）**：`plugins`（固定三张卡，永远有内容）、`bot_team`（空态在子页）、`about`/`more`/`browser`/`computer`（静态说明页，没有列表）、`feedback`（纯表单）。不算缺陷。
- **无错误态但合理（14 页）**：没有 IO 的页面不会失败，不需要错误态。
- **需要错误态而缺失（2 页）**：`settings_page_models`（读 `provider_config.json`，`main.rs:10780` 的「没读到 provider_config.json」走的是 note）、`settings_page_team_memory`（读记忆目录，损坏时静默空）。

**发现（低）：`settings_page_models` 读配置失败用 `note` 而非 `error`**。用户看到的是灰色提示条，与「页面正常但没有数据」在视觉上分不开。建议改成 `settings_error`（红底）。本轮**未改**：需要先确认 `provider_config.json` 不存在是「首次使用」还是「数据损坏」两种语义——前者应该引导创建（note 合适），后者才是 error。语义没定清之前改颜色会把「正常首次使用」误标成错误。列入 §9 待产品口径。

## 8. 长文本截断与溢出

```
overflow_y_scroll: 13 处      truncate(): 54 处
min_w(px(0.)):    65 处       line_clamp: 0 处
```

**发现（低）：17 处 `truncate()` 所在容器没有 `min_w(px(0.))` / `flex_1()` / 固定宽度**：

```
8894 9829 11041 12279 12288 12417 19180 19296 20819 21053
21884 23239 23250 23737 23745 24463 25798
```

抽查 `8894`、`12279`、`12417`、`19180`：它们的父容器是 `.flex().items_center()` 或 `.flex_col()`，`truncate()` 自身没有 `min_w(0.)`，在 gpui 里 `flex` 子项的 `min-width` 默认是 `auto`，长文本会把父容器撑开而不是省略。这些位置一旦遇到超长 Bot 名 / 超长路径 / 超长归档名，就会挤压右侧按钮或撑破卡片。

**这一轮不修**：17 处需要逐个确认父容器宽度语义（有些父容器本身是 `w_full` 的，实际不会撑破），改错会把本来正常的省略号去掉。列入 §9，建议下一轮按「先给父容器加 `min_w(px(0.))`，再逐页截图确认省略号仍在」的顺序做。

**长文本兜底存在**：13 处 `overflow_y_scroll` 覆盖了设置页内容区、详情面板、右栏（`chat-info-scroll`）、会话列表、消息流。

## 12. 一审二轮（Q-01 / Q-02 / Q-03 + 英文覆盖率复扫）

本节是提交 `9594301` 的增量，覆盖 §1 里那三行的旧结论。

### 12.1 Q-01 压缩状态行接进默认壳

`compaction_status_row()` 之前在全文只有两个调用点（`19395` / `19678`），都在 classic 的 `transcript()` 里；默认壳走 `wecom_transcript()`，`compacting` / `compaction_status_row` 均 0 命中。这不是"功能没做"，是接线漏了。

改法：默认壳的行序列是多行结构 `WecomRow`（虚拟列表按行测高），不能像 classic 那样在 `column` 里塞一个 `child`。新增 `WecomRow::Compacting` 变体：

```
3641   WecomRow::Compacting,                                    ← 变体定义
21664  WecomRow::Compacting => 70,                              ← wecom_row_fingerprint
21980  WecomRow::Compacting => mix(1),                          ← wecom_rows_fingerprint
22258  WecomRow::Compacting => compaction_status_row()...       ← wecom_row_el
27838  rows.push(WecomRow::Compacting);                         ← wecom_transcript
```

两个指纹函数必须同步补分支：虚拟列表靠指纹判断"行数没变但内容变了"，漏一支会导致压缩状态行出现时行高不重测。

位置选了**行尾**而不是行首：classic 的 `column` 顶上就是最新消息；`wecom_transcript` 的 `rows` 顶部是"加载更早"的历史区，滚上去才看得到，挂那儿等于没挂。

### 12.2 Q-02 命令面板入口

`wecom_composer()` 工具栏新增 `composer-plus`（`28588`），走 `on_palette_shortcut`，与 classic 同一条路径。

**键盘可达性按 @测试 的意见补上了**：只绑 `on_click` 是修了一半。现在与 classic 那枚按钮对齐：

```
track_focus(&plus_focus) + key_context("TabStop") + on_action(ActivateTabStop → on_palette_shortcut)

### 13.5 一个会误导所有人的 PowerShell 坑（我这轮踩到，写清楚免得再踩）

**`Get-Content` 在 BOM-less LF + 中文文件上会漏行。** 我在核 `browser_tools.rs:445` 时，`Get-Content` 报 1314 行、`Get-Content -Encoding UTF8` 报 1345 行、`[IO.File]::ReadAllLines` 报 1345 行，三者在同一台机器上不一致：

```
$ Get-Content src\browser_tools.rs           → 1314     ← 错，读成 ANSI 后中文续行被合并
$ Get-Content src\browser_tools.rs -Encoding UTF8 → 1345  ← 对
$ [IO.File]::ReadAllLines(...)                → 1345     ← 对
```

本机 `[Console]::OutputEncoding` 是 65001，但 `(Get-Culture).TextInfo.ANSICodePage` 是 936（GBK），于是 `Get-Content` 默认按 GBK 解码 UTF-8 字节，碰到中文就把行尾吃掉了。**仓库里这类文件有 94 个**（`docs/testing/0.5.1-acceptance.md` 418→502、`src/privacy.rs` 270→303、`src/browser_tools.rs` 1314→1345…），而 `src/main.rs`（CRLF）和 `src/i18n.rs`（CRLF）不受影响——这也解释了为什么以前没暴露。

**结论：核行号、写脚本一律用 `[System.IO.File]::ReadAllLines($path, [Text.Encoding]::UTF8)`，不要用 `Get-Content` 也不要用 `Get-Content -Encoding UTF8` 去数行。** 门禁脚本本身是对的（`verify-parity-anchors.ps1` 全线用 `ReadAllLines`），`ui-lint.ps1` 用的是 `ReadLines`，也正确；这个坑只坑手敲命令的人。

### 14.6 这几处是对的，不用动

- **`wechat-new-session` 与邻居完全一致**：`size(px(28.))`、`rounded(RADIUS_TAG)`、`hover(nav_item_hover_bg())`，位置在 `wechat-more` 左边，`is_bot_chat` 门控正确（`:27709-27727`）；`is_bot_chat` 在 `wecom_chat:27628` 已算好。群聊里不会出现点了没反应的按钮——这点很关键，`active_key()` 对群聊给的是 `group_key`，而三处 `backend.new_session` 传的都是 `bot_key`（`:6880`/`:7584`/`:20572`），不门控就会静默失败。
